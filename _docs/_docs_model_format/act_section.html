Bone Data Section

This section describes the actor's bones, including the hierarchy and pose position.

Header

Offset Type Description
0x0 Magic (0x007B7960 for Sluggers)
0x4 uint16 Actor ID
0x6 uint16 Bone count
0x8 uint32 First word of an embedded tree structure (unknown purpose)
0xc uint32 Root node pointer (relative to header). This is the second word of the tree structure and is used to traverse the bone hierarchy.
0x10 uint32 GEO name pointer (relative to header). This is the name of the geometry vertex file the bones are for.
0x14 uint16 Skin file id
0x16 byte[2] Padding
0x18 uint32 User data size
0x1c uint32 User data pointer (relative to header). Points at a chain of descriptors — see User data below.

Bone

Offset Type Description
0x0 uint32 Orientation control pointer (relative to header). This is an SRT that holds the bone's pose position, can be null. A null pointer means an identity local transform. It is mostly found on the extra root bones, but non-root bones have it too (chunk 18 bone 2, chunk 95 bone 1).
0x4 uint32 Previous sibling bone pointer (relative to header)
0x8 uint32 Next sibling bone pointer (relative to header)
0xc uint32 Parent bone pointer (relative to header)
0x10 uint32 First child bone pointer (relative to header)
0x14 uint16 GEO file ID: the index of the GPL submesh this bone draws rigidly. FFFF means the bone owns no mesh (it may still drive skinning of submesh 0 through SKN). See GEO ID ownership rules.
0x16 uint16 Bone ID
0x18 bool Is this bone positioned relative to its parent? (Usually true)
0x19 uint8 Something about draw priority, usually 0
0x1a byte[2] Padding

Section layout and tree links

Surveyed over all 203 models with an ACT section (2026-09-18). The layout is fully deterministic and has no slack:

0x00                  header (0x20 bytes)
0x20                  bone table: 0x1C x boneCount, in bone id order
0x20 + 0x1C*N         SRT array: 0x34 each, one per bone with a non-null SRT, in bone order
                      geo name, user data, padding (see Section tail)
  • Bone id equals table index. Every model has ids 0..N-1 in table order, with no gaps, aliasing or reordering.
  • The SRT array starts right after the bone table. Bone table end equals the first SRT offset (chunk 18: both 0xA14; chunk 95: both 0x5D0). The stride is a uniform 0x34, and no two bones share an SRT. So adding a bone shifts every byte after 0x20 + 0x1C*N, and the section has to be rebuilt, not patched.
  • The tree lives inside the bone records. Prev/next/parent/first-child (bone +0x04 to +0x13) are header-relative pointers into the bone table itself. Root bones are linked as siblings through the same prev/next fields, and the header's root pointer (+0x0C) acts as the first child of a virtual root.
  • The links are reproducible from parent ids alone. Processing bones in ascending id order and appending each one to the end of its parent's child chain (roots to the virtual root) reproduces every player model's prev/next/first-child/root pointers exactly (190 of 190).

GEO ID ownership rules

Surveyed across 721 exported models and confirmed in Dolphin (2026-09-16):

  • Rigid submeshes are placed by their owner bone. Every rigid (CompCount 3) submesh is named by at least one bone's GEO ID, and its vertices are stored in that bone's local space. Skinned (CompCount 6) submeshes are never named by a GEO ID.
  • An unowned submesh crashes the game. A GPL submesh appended without a bone that names it crashes on load (Invalid read from 0x00000008, PC = 0x804FF694). A new submesh and its owner's GEO ID must always be written together.
  • A GEO ID never exceeds the GPL submesh count.
  • One bone owns at most one mesh, because the field is a single uint16. In player models no two bones share a GEO ID. Seven effect and map-object models do give several bones the same GEO ID, so sharing is legal.
  • A bone that drives skinning may also own a rigid mesh. None does in vanilla data, but giving Mario's hand bone 28 a mesh worked: the mesh follows the hand and skinning is unaffected.
  • Submesh order doesn't have to follow bone order. Vanilla rigid submeshes are in ascending owner-bone order, but a submesh appended at the end on a lower-numbered bone draws correctly. Appending keeps every existing submesh index, and so every existing GEO ID and ptr7 facial SubmeshIndex, unchanged.
  • A single-bone prop can take a second bone and a second mesh. A bat (one bone that owns the bat mesh, no SKN section, ACT user data present) was given a new bone 1 under bone 0, with an appended rigid submesh owned by it. It drew correctly in game (Dolphin, 2026-09-29). Several new bones on the same prop also work: multiple new leaf bones and a chain of new bones, each owning its own appended submesh with its own texture (Dolphin, 2026-09-29).
  • In a stadium, a mesh must hang on a free vanilla root bone. In every stadium model, each bone that owns a mesh is a root bone (no parent) with its own SRT and no rotation. Tests in Yoshi Park, day and night models (sta03, sta03b, Dolphin):
    • A custom submesh on a new child bone under bone 0 drew nearly transparent, whatever its texture, vertex colours, position format or draw states. The same mesh on root bone 0 (a vanilla root without a mesh in both models), with its vertices moved into bone 0's space, drew opaque (2026-10-01).
    • On a vanilla root bone, the add-on's default output also draws correctly in both models: the builtin:rigid_spec_v1 list with Spec, s16 positions, white RGBA4444 vertex colours and normals, as a cube or a flat plane (2026-10-01).
    • A mesh on a new root bone does not draw at all (2026-10-02). Two planes on two new root bones (rotated, SRT type 12) in sta03 were invisible, although the patched block was checked byte by byte: route, bone chain and count, SRT blocks, GEO ID ownership, bounds table and vertex world positions were all correct. In a split build, the plane on vanilla bone 0 drew, and the plane on a new unrotated (SRT type 8) root bone stayed invisible in two runs. Why is unknown: the ACT bytes are right, so the stadium probably sets up its bone matrices from somewhere else.
    So the earlier child-bone result was probably the same new-bone problem; a vanilla child bone has never been tested. The rule the tools enforce in every stadium model (dirs 7-16, only Yoshi Park tested): the host bone must be a vanilla root bone without a mesh, and new bones are refused (see Appending bones). Stadiums have few such bones: one in sta03 (bone 0, at the origin), 19 in sta03b. All custom geometry of sta03 therefore has to share one custom submesh on bone 0.

The bone table is reached through the tree: the tree header sits at header+0x08 and its root pointer at header+0x0C. Each node address is the bone's start, relative to the ACT header. BlockValidator walks it to check the rules above.

High- and low-poly pairs share one skeleton

Each player character has a high-poly model and a low-poly L_* model, stored as file indices n and n + 1 of the same chunk. Their ACT geo names match once the L_ prefix and the extension are removed; the Mii pairs mix .gpl and .gplp. All 66 vanilla pairs have the same bone count, and 56 have identical parent, track and mirror tables.

The game poses the low-poly model with the high-poly model's bones. Confirmed in Dolphin with Mario (2026-09-27), after appending a bone 91 to one or both models:

  • A low-poly model may only draw on bones the high-poly model has. L_mario with a mesh on its new bone 91 crashed on model load while HP Mario had 91 bones (0-90). The same mesh on existing bone 49 loaded, even with the unused bone 91 still present. Adding bone 91 to HP Mario as well made the mesh on bone 91 load. An extra bone that owns no mesh is harmless.
  • The low-poly model's own placement of a bone is ignored. With HP Mario's bone 91 parented to the arm and L_mario's bone 91 still parented to the head, L_mario's mesh followed the arm.
  • The reverse is fine. HP Mario drawing on a new bone 91 while L_mario had only 91 bones worked (Dolphin, 2026-09-18).

The hammerspace patcher checks the pair against the partner's currently patched state. It refuses a patch or unpatch that would leave the low-poly model drawing on a bone the high-poly model lacks. It warns when an appended bone's parent or SRT differs between the two models.

User data

Found while investigating (2026-09-18) what silently counts bones outside the header's own boneCount. The header's user data pointer (0x1c) is null when userDataSize (0x18) is 0 — dozens of models ship no user data at all with a perfectly working bone tree. When present, it points at a chain of descriptors, each read until the header's total userDataSize is consumed:

Offset Type Description
0x0 uint32 Descriptor size in bytes, including this 0x0C-byte header
0x4 uint16 Kind (see below)
0x6 uint16 Count (meaning depends on kind)
0x8 uint32 Data pointer (relative to header)

Three kinds are seen across the corpus:

  • Kind 3 — bone-to-track table. uint16[boneCount], indexed by bone id, giving the ANM track id that bone's animation reads from. 0xFFFF means "no track" — a normal, shipped state (every player model has some: 13-14 trackless bones on Mario). This is the one kind act_section.html previously alluded to as "linking information between bones and animation tracks."
  • Kind 2 — the mirror table. (uint8 mirror_bone_id, uint8 role)[boneCount], indexed by bone id. Almost certainly the left/right mirroring used for lefty/righty batting stances. On every player model checked, this table is a perfect involution: table[table[i]] == i for every bone. role values seen: 1 = the main root, 2 = one of five extra root bones, 3 = an ordinary bone (a bone that mirrors itself, i.e. a centreline bone, is simply (own_id, 3) — 23-38 of these per model), 0/4 = rare one-offs of unknown meaning (chunk 18 bone 54 is role 0; chunk 95 bone 17 is role 4). Two donors (chunk 37/1 and 51/1, plus three Magikoopa recolor siblings 52/1, 53/1, 54/1) have oversized, non-involution mirror tables with (0,0) holes and duplicate bone ids — these do not fit this model and are treated as out of scope by tooling that rebuilds this section. Because mirror ids are stored as uint8, bone ids in a rebuilt skeleton must stay <= 255; a corrupt mirror table was confirmed in Dolphin to fail silently (no crash, no visible glitch), so there is no in-game signal to catch a bad table after the fact.
  • Kind 4 — opaque, bone-independent. Seen on nine models. Each entry is (uint16 track_id, uint16 = 2), with the descriptor's own count field matching (size - 0x0C) / 4. It references animation tracks, not bones, so it is unaffected by the bone count and can be treated as an opaque blob to copy through verbatim.

The kinds are independent: some models carry only a kind-3 table and no mirror table (chunks 130/18, 137/74, 137/139, 142/129). Models without any user data include chunks 5, 7, 9-12, 15, 16, 126-129, 137, 142 and 159.

Every player model's bone table is exactly boneCount entries, ids 0..boneCount-1 in table order with no gaps — the mirror and track tables are the only place a bone count appears outside the header, and this is why extending the bone table (e.g. appending new bones) requires rebuilding kinds 2 and 3 alongside it, while any kind-4 entry can simply be carried through unchanged.

SRT

SRT stands for scale, rotation, transform.

Offset Type Description
0x0 uint8 Type: a component-presence mask, see SRT type byte
0x1 byte[3] Padding
0x4 float[3] Scale (x, y, z)
0x10 float[4] Quaternion stored as (x, y, z, w). Note: when applying this quaternion, negate w and reorder to (-w, x, y, z) to match the game's convention.
0x20 float[3] Translation (x, y, z)
0x2c byte[8] Padding? Don't know why it's here.

SRT type byte

The type byte says which components the game reads. Bit 0x4 means "rotation is live", bit 0x8 means "translation is live". The game ignores any component whose bit is not set. Surveyed over the player corpus (about 4,000 bones with an SRT, 2026-09-19):

Type Bones Non-identity rotation Non-zero translation
04880%0%
481100%0%
814690%62%
121903100%94%

There are no exceptions in either direction. Types with bit 0x1 set (1, 5, 9, 13) have identity scale, rotation and translation everywhere and mean something else. No vanilla bone has a non-unit scale, so no scale bit is known.

So a new bone's type byte must be derived from the values written, never copied from its parent. Found in game: a new bone that copied its translation-only parent's 8 lost its own rotation, and the mesh on it rendered at Mario's chest instead of above his cap, rotated 180 degrees about the bone. The Blender exporter now computes the mask from the bone's rotation and translation, and warns about a non-unit scale.

Appending bones

New bones can be appended to a skeleton as long as nothing about the existing bones changes. Confirmed in Dolphin (2026-09-18 to 2026-09-20):

  • An inert leaf changes nothing. Mario with bone 91 appended under the spine (bone 3), with no mesh, no track and self-mirrored, played an at-bat with no visible or behavioural change.
  • A new bone is live. A rigid submesh owned by the new bone followed the spine through every animation. A chain of four new bones, each parented to the previous one and each with its own cube, also followed Mario correctly.
  • No bone-matrix cap was found up to 115 bones. Mario with 24 appended bones (91 to 115) played normally. The largest vanilla skeleton has 131 bones (chunk 66); player characters have 52 to 107.
  • Different donors work. King Boo (different bone count and root layout), Noki (chunk 42, with a kind-4 user data entry copied through unchanged) and a donor with no user data at all (chunk 136 sta03_yoshi_train02, 3 bones) all worked with a submesh on a new bone.
  • A wrong mirror entry fails silently. Bone 91 mirrored to bone 1 instead of itself caused no crash and no visible glitch.

Why appending is safe: nothing outside the ACT counts bones. Player models have ptr6 = ptr8 = 0, and ptr7 (facial poses) indexes submeshes, not bones. GPL, TEX and SKN have no bone counter. SKN refers to bones by id, ANM is looked up by track id (a new bone has track 0xFFFF and is skipped), and the bat/glove attach points in main.dol use bone ids too. Keeping every existing id keeps all of these valid. The one exception is the high-/low-poly pair, see above.

Changing existing topology is not safe, and the result is silently wrong rather than a crash:

  • Reparenting an existing bone changes its bind matrix while its ANM track still drives the old animated matrix. The mismatch shows as a shear at bind pose.
  • Inserting a new bone between two existing bones is a reparent of the child. ANM translation keys are parent-relative (24 of 24 characters checked), so the limb animates against the wrong parent.
  • Reordering a sibling chain changes tree evaluation order. Whether the game cares is unknown, possibly through the draw-priority byte at bone +0x19.

Appending a new bone at the end of its parent's child chain adds a link without disturbing any existing one, so it is the only topology change allowed.

New root bones draw nothing in stadiums, and new bones are refused there. A new root bone is written with a null parent pointer and linked after the last root in the root sibling chain, which starts at the header's root pointer (+0x0C). That adds a link at the end of an existing chain, like a leaf append. The header word at +0x08 is left alone: across all exported models it is 0xC or a stale-looking address, never anything that tracks the roots. This layout was built for stadiums, where a mesh must hang on a root bone, but a mesh on such a bone did not draw (Yoshi Park, Dolphin, 2026-10-02; see GEO ID ownership rules). The patcher now refuses new root bones in every model, and any new bone in a stadium (dirs 7-16). act_rebuild.append_leaf_bone(parent_id=None) still builds the layout, for future tests.

The hammerspace patcher enforces this before writing:

  • Every existing bone keeps its id, parent and mirror pair. Its GEO ID stays unchanged unless a custom submesh claims it.
  • New bone ids continue contiguously from the donor's count, the total stays <= 255 (the mirror table stores uint8 ids), and every new bone has a parent. Stadium models (dirs 7-16) take no new bones at all.
  • No existing bone may be parented to a new bone.
  • A new bone has track 0xFFFF and mirrors itself with role 3.
  • No SKN record may name a new bone: new bones never drive skinning.
  • The donor's mirror table must be absent or a clean boneCount-long involution.

Section tail and alignment

The ACT section starts on a 32-byte boundary, like every section (see overview). Its inside has no single alignment formula. The geo-name strings follow the SRT blob directly, with no reserved null-terminator byte in the layout. The padding after the names and user data, up to the section end, varies per donor. It depends on the section that follows ACT in the model block, not on anything inside ACT (185 player models rebuilt byte-identical this way).

act_rebuild therefore recomputes the bone table and SRT blob, which shift when the bone count changes. It carries the name/tail region through verbatim and leaves section alignment to BuildHEADERModelBlock.
