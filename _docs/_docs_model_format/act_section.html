Bone Data Section

This section describes the actor's bones, including the hierarchy and pose position.

Header

Offset Type Description
0x0 Magic (0x007B7960 for Sluggers)
0x4 uint16 Actor ID
0x6 uint16 Bone count
0x8 uint32 First word of an embedded tree structure (unknown purpose)
0xc uint32 Root node pointer (relative to header). This is the second word of the tree structure and is used to traverse the bone hierarchy.
0x10 uint32 GEO name pointer (relative to header). This is the name of the geometry vertex file the bones are for.
0x14 uint16 Skin file id
0x16 byte[2] Padding
0x18 uint32 User data size
0x1c uint32 User data pointer (relative to header). Points at a chain of descriptors — see User data below.

Bone

Offset Type Description
0x0 uint32 Orientation control pointer (relative to header). This is an SRT that holds the bone's pose position, can be null.
0x4 uint32 Previous sibling bone pointer (relative to header)
0x8 uint32 Next sibling bone pointer (relative to header)
0xc uint32 Parent bone pointer (relative to header)
0x10 uint32 First child bone pointer (relative to header)
0x14 uint16 GEO file ID: the index of the GPL submesh this bone draws rigidly. FFFF means the bone owns no mesh (it may still drive skinning of submesh 0 through SKN). See GEO ID ownership rules.
0x16 uint16 Bone ID
0x18 bool Is this bone positioned relative to its parent? (Usually true)
0x19 uint8 Something about draw priority, usually 0
0x1a byte[2] Padding

GEO ID ownership rules

Surveyed across 721 exported models and confirmed in Dolphin (2026-09-16):

  • Rigid submeshes are placed by their owner bone. Every rigid (CompCount 3) submesh is named by at least one bone's GEO ID, and its vertices are stored in that bone's local space. Skinned (CompCount 6) submeshes are never named by a GEO ID.
  • An unowned submesh crashes the game. A GPL submesh appended without a bone that names it crashes on load (Invalid read from 0x00000008, PC = 0x804FF694). A new submesh and its owner's GEO ID must always be written together.
  • A GEO ID never exceeds the GPL submesh count.
  • One bone owns at most one mesh, because the field is a single uint16. In player models no two bones share a GEO ID. Seven effect and map-object models do give several bones the same GEO ID, so sharing is legal.
  • A bone that drives skinning may also own a rigid mesh. None does in vanilla data, but giving Mario's hand bone 28 a mesh worked: the mesh follows the hand and skinning is unaffected.
  • Submesh order doesn't have to follow bone order. Vanilla rigid submeshes are in ascending owner-bone order, but a submesh appended at the end on a lower-numbered bone draws correctly. Appending keeps every existing submesh index, and so every existing GEO ID and ptr7 facial SubmeshIndex, unchanged.

The bone table is reached through the tree: the tree header sits at header+0x08 and its root pointer at header+0x0C. Each node address is the bone's start, relative to the ACT header. BlockValidator walks it to check the rules above.

User data

Found while investigating (2026-09-18) what silently counts bones outside the header's own boneCount. The header's user data pointer (0x1c) is null when userDataSize (0x18) is 0 — dozens of models ship no user data at all with a perfectly working bone tree. When present, it points at a chain of descriptors, each read until the header's total userDataSize is consumed:

Offset Type Description
0x0 uint32 Descriptor size in bytes, including this 0x0C-byte header
0x4 uint16 Kind (see below)
0x6 uint16 Count (meaning depends on kind)
0x8 uint32 Data pointer (relative to header)

Three kinds are seen across the corpus:

  • Kind 3 — bone-to-track table. uint16[boneCount], indexed by bone id, giving the ANM track id that bone's animation reads from. 0xFFFF means "no track" — a normal, shipped state (every player model has some: 13-14 trackless bones on Mario). This is the one kind act_section.html previously alluded to as "linking information between bones and animation tracks."
  • Kind 2 — the mirror table. (uint8 mirror_bone_id, uint8 role)[boneCount], indexed by bone id. Almost certainly the left/right mirroring used for lefty/righty batting stances. On every player model checked, this table is a perfect involution: table[table[i]] == i for every bone. role values seen: 1 = the main root, 2 = one of five extra root bones, 3 = an ordinary bone (a bone that mirrors itself, i.e. a centreline bone, is simply (own_id, 3) — 23-38 of these per model), 0/4 = rare one-offs of unknown meaning (chunk 18 bone 54 is role 0; chunk 95 bone 17 is role 4). Two donors (chunk 37/1 and 51/1, plus three Magikoopa recolor siblings 52/1, 53/1, 54/1) have oversized, non-involution mirror tables with (0,0) holes and duplicate bone ids — these do not fit this model and are treated as out of scope by tooling that rebuilds this section. Because mirror ids are stored as uint8, bone ids in a rebuilt skeleton must stay <= 255; a corrupt mirror table was confirmed in Dolphin to fail silently (no crash, no visible glitch), so there is no in-game signal to catch a bad table after the fact.
  • Kind 4 — opaque, bone-independent. Seen on nine models. Each entry is (uint16 track_id, uint16 = 2), with the descriptor's own count field matching (size - 0x0C) / 4. It references animation tracks, not bones, so it is unaffected by the bone count and can be treated as an opaque blob to copy through verbatim.

Every player model's bone table is exactly boneCount entries, ids 0..boneCount-1 in table order with no gaps — the mirror and track tables are the only place a bone count appears outside the header, and this is why extending the bone table (e.g. appending new bones) requires rebuilding kinds 2 and 3 alongside it, while any kind-4 entry can simply be carried through unchanged.

SRT

SRT stands for scale, rotation, transform.

Offset Type Description
0x0 uint8 Type (I've seen 0x4, 0x8, and 0xc, but they all seem to behave the same)
0x1 byte[3] Padding
0x4 float[3] Scale (x, y, z)
0x10 float[4] Quaternion stored as (x, y, z, w). Note: when applying this quaternion, negate w and reorder to (-w, x, y, z) to match the game's convention.
0x20 float[3] Translation (x, y, z)
0x2c byte[8] Padding? Don't know why it's here.

Section tail and alignment

The ACT section starts on a 32-byte boundary, like every section (see overview). Its inside has no single alignment formula. The geo-name strings follow the SRT blob directly, with no reserved null-terminator byte in the layout. The padding after the names and user data, up to the section end, varies per donor. It depends on the section that follows ACT in the model block, not on anything inside ACT (185 player models rebuilt byte-identical this way).

act_rebuild therefore recomputes the bone table and SRT blob, which shift when the bone count changes. It carries the name/tail region through verbatim and leaves section alignment to BuildHEADERModelBlock.
